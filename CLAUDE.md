# OffCampus

Last-mile ride-share Android app for college students: form travel "lobbies" heading the same way from a station/gate at a similar time, coordinate in-app chat, book the actual ride via Uber/Ola/Rapido deep links, split the fare with a two-way payment acknowledgement.

## Tech stack
- Kotlin, Jetpack Compose (Material 3) — no XML layouts
- Firebase: Authentication (college email), Firestore, Cloud Functions (matching/notification/acknowledgement logic)
- MVVM: ViewModel + StateFlow feeding Composables, no business logic inside Composables
- No payment gateway, no live GPS, no in-house driver network — ride booking hands off to Uber/Ola/Rapido via deep links

## Design system (Phase 0 — approved design brief lives at the artifact link in conversation history)
Concept: "streetlight & meter" — the actual moment of waiting at a gate at dusk for a shared auto. Quiet neutral surfaces; amber/violet/green/coral used only for actions and status, not decoration. Cards clip one corner like a ticket stub (`RoundedCornerShape(16,16,16,3)`); buttons stay full pill.

**Color roles (light / dark):**
- Background: `#F7F5FB` / `#171226`
- Surface: `#FFFFFF` / `#201A35`
- Primary (violet): `#6753E8` / `#9384FF`
- Action (amber): `#E8940E` / `#F5A524`
- Success/settled (green): `#1E9463` / `#3FCB90`
- Alert/owed (coral): `#D8492F` / `#FF7A5C`

**Typography:**
- Display/headlines: Bricolage Grotesque (bold, personality — app name, empty states, headers)
- Body/UI: Manrope (lists, chat, buttons)
- Numerals (fares, timestamps, seat counts): JetBrains Mono, tabular

**Spacing:** 4dp base grid — 4/8/12/16/24/32/48/64.

**Motion:** spring-based (damping ~0.8, ~200-300ms). Lobby list uses `AnimatedVisibility` (fade+scale) and `animateContentSize` for seat-count changes. Chat bubbles slide up 12dp + fade in. Payment ack crossfades chip color + morphs a checkmark on settle.

Once `Color.kt` / `Type.kt` / `Theme.kt` exist, every screen must use them — flag any screen that drifts during self-review.

## Post-launch fixes
Bug fixes and small changes found after Phase 11 closed, not tied to any numbered phase.

- **Fix 1 — Auto capacity validation** (found during a post-completion test pass): `maxSize` was a flat 2-6 range regardless of ride type, so an Auto trip (a real auto-rickshaw seats 3 passengers, full stop) could be posted for a group of 4-6 — the default form state was even invalid out of the box (`maxSize = 4` paired with default `rideType = AUTO`). Fixed with `groupSizeOptions(rideType)` in `PostTripViewModel.kt` (Auto → 2..3, Cab → 2..6 unchanged), with the group-size selection auto-clamped down if it's out of range when switching to Auto. The same cap is now enforced in `firestore.rules`'s `lobbies` create rule too (deployed live), so a raw API call bypassing the app can't do it either. The two pre-existing seeded Auto lobbies that already violated this were patched in both `seed/seed.js` and the live Firestore data.

- **Fix 2 — Rider ratings** (feature gap: `ratingAverage`/`ratingCount` existed on `Rider` and rendered on `ProfileScreen.kt` since Phase 1, but nothing ever wrote to them — every rider showed "No ratings yet" forever). Added a new top-level `ratings` collection (`data/model/Rating.kt`: `lobbyId`, `raterUserId`, `ratedUserId`, `stars`, `timestamp`), doc id deterministically `{lobbyId}_{raterUserId}_{ratedUserId}` so rating the same person twice for the same trip corrects the existing document instead of double-counting. A "Rate" text action sits next to "Report" on every non-self participant row in `PaymentSplitScreen.kt` (plus a "Rate" link next to "Paid by ..." for participants rating the payer), opening `ui/rating/RateRiderScreen.kt` + `RateRiderViewModel.kt` — a 5-star picker matching the "★"/"☆" glyphs `ProfileScreen.kt` already used to display ratings read-only. `RateRiderViewModel.submit()` runs one Firestore transaction that reads any prior rating from this rater for this trip, reads the rated rider's current rollup, and writes both the rating doc and the adjusted `ratingAverage`/`ratingCount` atomically — same transaction-first pattern as `PaymentSplitViewModel.acknowledge()`. `firestore.rules` gained a third narrow `riders` update carve-out (`isRatingUpdate`) alongside the friendIds one from Phase 9, with the same honest limit: the rule can confirm the *result* lands in a plausible range (count holds steady or grows by exactly one, average stays in [0, 5]), not that the arithmetic that produced it was honest — a real fix needs a Cloud Function to own the computation, same conclusion as the payment-ack case. Scope choice: rating only covers payer↔participant pairs (mirroring where Report already lives), not participant-to-participant when neither is the payer — the payment split screen has no UI slot for that today. One real bug found and fixed during testing: the `ratings` read rule originally dereferenced `resource.data` unconditionally, which denies outright when the document doesn't exist yet — and `RateRiderViewModel.submit()`'s transaction always reads that exact doc first (to check for a prior rating) before it necessarily exists, so every first-ever rating failed with `PERMISSION_DENIED` until the rule was changed to allow reading a not-yet-existing document.

- **Fix 3 — Passwordless college-email sign-in** (feature request: sign in with just a college email, no password, the way Google apps let you "continue" without retyping a password). Went with Firebase Auth's **email link** ("magic link") method rather than Google Sign-In, since Google Sign-In only proves anything if the college's student email is actually Google-Workspace-backed, which isn't something this project can verify — email link works with any real inbox. The harder part wasn't Firebase Auth itself, it was getting the link to open *this app* instead of a browser: **Firebase Dynamic Links — the service that used to make an email-link URL smart enough to hand off to a mobile app — shut down in 2025**, so that hand-off now has to be built by hand with real Android **App Links**. `public/index.html` + `public/.well-known/assetlinks.json` are deployed to Firebase Hosting (`offcampus-5f370.web.app`), `assetlinks.json` declares the app's signing certificate so Android will trust the association, and `AndroidManifest.xml`'s `MainActivity` gained a second, `autoVerify="true"` intent-filter for that host plus `launchMode="singleTop"` so a link tapped while the app is already open re-delivers through `onNewIntent` instead of spawning a second instance. `AuthViewModel.sendMagicLink()` calls `sendSignInLinkToEmail` with an `ActionCodeSettings.url` pointing at that hosted page, and stashes the email in `SharedPreferences` (`PREF_PENDING_EMAIL`) — Firebase's own completion call needs the email back, and the link itself doesn't carry it. `MainActivity` forwards whatever URI launched or re-launched it to `AuthViewModel.handleEmailLinkIntent()`, which no-ops unless `auth.isSignInWithEmailLink()` recognizes it. One real gap the password flow never had: a magic link creates the Firebase Auth user immediately on tap, with no separate step that ever asked for a name — so `AuthUiState` gained a `NeedsProfile` case, and `AuthScreen` shows a one-time "what's your name?" step (`completeProfile()`) before treating a fresh magic-link signup as fully signed in; a returning user with an existing Rider doc skips straight through. Two deliberate limitations, both flagged in-code: completing the link only works on the same device/app install that requested it (the pending email lives in that install's own SharedPreferences, not synced anywhere); and `assetlinks.json` currently only lists this machine's **debug** keystore's SHA-256 fingerprint — a release build's own signing certificate has to be added as a second entry in that file before a signed release APK's links would verify. Verified end-to-end against the live Firebase project (not just compiled): enabled the Email Link provider on the project (it ships disabled), generated real sign-in links via the Admin SDK for a throwaway test account, and drove the whole chain on the emulator — send → tap → sign-in → name step → Rider doc created → avatar picker — confirming both server-side (a real Firebase Auth user and Firestore Rider doc were created) and on-screen. One `adb`-only gotcha surfaced along the way: `adb shell` re-parses `&` through the device's own shell, silently truncating a URL's query string unless each `&` is escaped — worth knowing if this flow ever needs re-testing by hand from a shell; it isn't a bug in the app.

A **real bug** did surface, though, the first time this was tested against an actual inbox rather than a throwaway Admin-SDK link: tapping a genuine email link dropped the account straight into the Lobbies screen with **no Rider document ever created** — skipping the name step entirely. Root cause: `AuthViewModel`'s `addAuthStateListener` (there since Phase 2, to restore a persisted session on cold start) fires the instant Firebase's SDK completes `signInWithEmailLink`, same as any other auth-state change — and it unconditionally set `AuthUiState.SignedIn`, with no notion that a magic-link user might not have a Rider document yet. That write raced the deliberate Rider-doc check already sitting at the end of `handleEmailLinkIntent`, and the listener's blind write was winning. Fixed by giving both paths one shared `resolveSignedInState(uid, email)` — it's the only place that decides `SignedIn` vs `NeedsProfile` now, so the two can race all they want and still land on the same correct answer. On a Firestore read failure it deliberately leaves `uiState` untouched rather than guessing `NeedsProfile` for an already-registered user — `completeProfile()` does a full document `set()`, so guessing wrong there would have overwritten a real user's avatar/ratings/friends with fresh defaults.

- **Fix 5 — Friend search-as-you-type** (feature request: finding a friend by typing part of their name or email and picking from live suggestions, the way Instagram's people search works, instead of typing a stranger's full college email exactly). Firestore has no built-in "contains anywhere" text search — the standard workaround, already used elsewhere in this project's rules, is a **prefix range query**: `.orderBy(field).startAt(prefix).endAt(prefix + '')` matches every value that *starts with* the typed text. `FriendsViewModel.search()` runs that as two separate range queries (Firestore can't `OR` across two different fields in one query) — one on `name`, one on `email` — merges the results by document id, and drops the current user and existing friends from the list, since suggesting either is never useful. A 300ms debounce (`searchJob?.cancel()` + a fresh `delay(300)` before each query) keeps a fast typist from firing a Firestore read per keystroke. `sendRequest()` (which used to do its own exact-email lookup) became `sendRequestTo(target: Rider)` — tapping a suggestion row sends the request directly, keeping all the same guardrails (no self-requests, no duplicate friends, no duplicate pending requests) minus the now-redundant "does this email exist" check, since a suggestion is already a resolved rider.

- **Fix 6 — Lobby riders shown before joining, not just a seat count** (safety concern: joining a lobby with only "2 / 3 riders" to go on gives no idea who you'd actually be traveling with). `LobbyDetailViewModel` now resolves `lobby.memberIds` into full `Rider` objects (name + avatar) the same way `FriendsViewModel` resolves a friends list, re-fetching only when the member id list itself actually changes rather than on every snapshot (a lock/status change alone shouldn't re-trigger it). Shown **inline** on the lobby detail screen, directly under the rider count — not a separate screen — since with lobbies capped at 3 or 6 riders the list is always short, and a safety-relevant detail like "who's actually in this lobby" should be visible at the exact moment someone's deciding whether to tap "Join," not one extra tap away.

- **Fix 7 — `assetlinks.json` had the wrong signing fingerprint** (found installing the app on a real phone via USB for the first time, not the dev machine's emulator). App Links verification kept failing silently — `assetlinks.json` listed the SHA-256 of a debug keystore generated once by hand at `~/.android/debug.keystore` while chasing an unrelated JDK issue, but `./gradlew signingReport` showed Gradle's *actual* debug build was signed with a completely different keystore living at `D:\Android\.android\debug.keystore` — two debug keystores existed on the same machine, and the one the file vouched for was never the one signing real builds. Fixed by publishing the real fingerprint from `signingReport` and deleting the unused hand-made keystore so it can't cause the same confusion again. Worth remembering for anyone re-running this project fresh: **always confirm the fingerprint with `signingReport` right before touching `assetlinks.json`**, don't assume any single `debug.keystore` path is the one in play — Android Studio, a plain `gradlew` invocation, and a manually created keystore can all disagree about which file that is.

- **Fix 8 — Ride booking and ending the ride restricted to the lobby master** (permissions gap: locking a lobby was already master-only, both in `LobbyDetailScreen.kt` and in `firestore.rules`'s `isLockingLobby()`, but once a lobby *was* locked, `LockedRideBookingCard` — the Uber/Ola/Rapido links plus "Ride's done — split the fare" — was shown to every member, not just whoever locked it). `LobbyDetailScreen.kt`'s status `Crossfade` now branches on `isMaster` for the `LOCKED` case: the master still sees the exact same booking card as before, everyone else sees a new `LockedRideInProgressCard` with no buttons at all — just a status line that the master's booking the ride and will post the fare split when it's done. Chat access is unaffected either way, it was never gated by role. The client-side change alone wasn't enough, though — `firestore.rules`'s `isCompletingLobby()` originally let *any current member* flip a locked lobby to `COMPLETED` ("whoever paid is the one posting the split", a deliberate Phase 7 call) — narrowed to `request.auth.uid == resource.data.createdBy` so a non-master member can't just call the Firestore write directly and bypass the UI gate, the same defense-in-depth pattern Fix 1 used for the Auto seat cap. Deployed live.

- **Fix 9 — Friend-lobby Snackbar is now clickable** (the in-app "X posted a trip to Y" notification from `LobbyBrowseViewModel` told you something happened but gave no way to act on it — you had to go find the lobby yourself in the list). `_friendLobbyNotification` changed from a bare `String?` to a small `FriendLobbyNotification(message, lobbyId)`, since the lobby's own id was already sitting right there in `notifyFriendLobby(lobby: Lobby)` and just wasn't being carried along. `LobbyBrowseScreen.kt` passes that id through Compose's own Snackbar action button (`actionLabel = "View"`) rather than making the whole Snackbar row a giant tap target — `showSnackbar()` returns whether the action was actually tapped versus the Snackbar just timing out, and only in the tapped case does it call `onOpenLobby(lobbyId)`. Deliberately scoped to *this* Snackbar only — `PaymentNotificationViewModel`'s "you owe ₹X" Snackbar wasn't touched, since it wasn't part of this request. **Outside-app notification (a real push when the app isn't running at all) was explicitly requested to be looked into and explicitly declined**: it needs a Cloud Function calling FCM in response to the Firestore write, and Cloud Functions requires the Firebase project on the paid Blaze plan even at zero real usage cost, since Google requires a billing account attached at all — not something this project wants to take on. The only real lever left without it: on Android builds that kill backgrounded apps aggressively (OnePlus/OxygenOS notably), disabling battery optimization for this app keeps its process — and this live Firestore listener — alive longer in the background, which is as close to "notified without opening the app" as the free tier allows.

- **Fix 10 — Custom profile photo, without Firebase Storage** (feature request: let a rider upload their own photo instead of only picking from the 8-avatar catalog — the Phase 0 brief's "no real photos" was a deliberate design call at the time, revisited here at explicit request). The obvious way to store an uploaded photo is Firebase Storage, but Storage needs the paid Blaze plan the same as Cloud Functions does, and billing was explicitly ruled out. The free-tier path instead: `AvatarPickerScreen.kt`'s new "Upload a photo" button uses `ActivityResultContracts.GetContent()` to open the system photo picker (no runtime permission needed on modern Android), then `PhotoCompression.kt` center-crops whatever's picked to a square, downscales it to 128×128, and JPEG-compresses it — the result is base64-encoded straight into a new `Rider.photoBase64` field instead of a Storage file reference. At that resolution a real photo lands somewhere around a few KB, comfortably inside Firestore's 1MiB document cap and small enough that every screen reading a rider's name for its own reasons (friend list, lobby member list, chat) doesn't meaningfully suffer from also pulling those bytes along, which was the trade-off worth naming honestly rather than building around quietly. `AvatarView.kt` now takes an optional `photoBase64` and renders it (decoded once per value via `remember`, not on every recomposition) in place of the catalog emoji whenever it's non-blank — a real photo always wins over `avatarId` when both are present, and picking a catalog avatar afterward explicitly clears `photoBase64` back to empty (`ProfileViewModel.updateAvatar()`/`updatePhoto()` are mutually exclusive writes), so the two never end up silently disagreeing about which one is "the" avatar. `AvatarPickerScreen.kt` already served both first-time signup and later "change avatar" from Profile before this fix, so building the upload flow there once covers both asks in the original request with no separate code path. Wired through everywhere a full `Rider` object was already in hand — Profile, friends list, incoming friend requests, friend search results, lobby member rows, fare-split participant rows — deliberately **not** wired into chat bubbles, the report screen, or the rate-rider screen, since those only carry a bare `avatarId` string today and plumbing a real `Rider` through each would be its own separate change; they still show the catalog avatar correctly, just never a custom photo. Verified end-to-end on the emulator with a real picked image, not just compiled: opened the system photo picker, selected a test photo, confirmed the live preview decoded and cropped it correctly, saved, and confirmed server-side that `Rider.photoBase64` actually persisted to Firestore at the expected small size.

- **Fix 11 — Profile photos moved to a Cloudflare Worker + KV** (the instructor asked for Cloudflare, and it also removes Fix 10's compromise of photo bytes riding along inside every rider document). A Cloudflare **Worker** (`worker/src/index.js`) is the trusted middleman the app can't be: `POST /photo` and `DELETE /photo` require the rider's **Firebase ID token**, which the Worker verifies itself with WebCrypto (RS256 signature against Google's published `securetoken` keys, then `exp`, `iat`, `aud` = this project, `iss`, and a sane `sub`) — no dependencies. The storage key is built from the uid **inside the verified token**, never from anything in the request, so a rider can only ever write their own photo. Uploads must start with the JPEG magic bytes and be at most 300 KB. `GET /photo/<uid>` is public so an image loader can use it; responses are `immutable`-cacheable because every upload returns a URL with a fresh `?v=`. **KV** rather than R2 because it needs no payment method (R2 may). `Rider.photoUrl` now holds that URL; `Rider.photoBase64` is kept as a read-only legacy field so Fix 10's photos still display until replaced. App side: `PhotoService` (`HttpURLConnection`, ID token from `getIdToken`), `compressImageToJpeg` (256px square JPEG, ~10-40 KB), Coil's `SubcomposeAsyncImage` in `AvatarView` with the catalog avatar as loading/error fallback (priority: `photoUrl` > `photoBase64` > catalog), and `ProfileViewModel` now surfaces failures (a network upload can genuinely fail, unlike the old Firestore-only write) and best-effort deletes the stored file when a rider switches back to a preset avatar. Also fixed a Fix 10 leftover: the picker's preview kept showing the old photo after tapping a preset. The Worker URL comes from `BuildConfig.PHOTO_WORKER_URL`, overridable via `photoWorkerUrl` in the git-ignored `local.properties`; a **debug-only** network security config allows plain http to `localhost` so a local `wrangler dev` can be tested — release builds stay https-only. Verified for real: the Worker against live Firebase tokens (missing token, tampered token, non-JPEG, unknown uid and delete all behaved), then the whole app flow on the emulator through `adb reverse` (pick photo → `POST /photo` 200 → Firestore `photoUrl` set → Coil `GET` 200 → rendered on Profile; switching to a preset → `DELETE` 200 → photo 404). **Deployed** to `https://offcampus-photos.offcampus.workers.dev` (the account's workers.dev subdomain is `offcampus`, the KV namespace id is committed in `worker/wrangler.toml` — an identifier, not a secret) and re-run against the live deployment with real Firebase tokens: upload 200, fetch returns the same bytes, no-token and tampered-token 401, non-JPEG 415, delete then 404. Redeploy after any Worker change with `npx wrangler deploy` from `worker/`. Limitations: KV is eventually consistent (a new photo can take about a minute to appear elsewhere), photos are public to anyone who knows a uid, and there is no rate limiting.

- **Fix 12 — A single unread-activity alert, not a count or a new tab** (feature request, after two heavier options — a dedicated "Chats" tab, or per-item badges — were explicitly turned down in favor of one simple presence signal: "let the user know some message or friend request is pending"). The Friends tab's badge, which used to show the pending-friend-request *count*, now shows a plain dot (`Badge()` with no content, Material3's built-in dot style) that lights up if *either* a friend request is pending *or* any chat — lobby or friend — has a message this rider hasn't seen. The same dot appears on a lobby's own card in the browse list if that specific lobby's chat has something unread, so the alert isn't just "something, somewhere" — a lobby you're in tells you directly. There's deliberately no unread *count* anywhere: Firestore has no cheap way to total exact unread messages across a changing set of chats, but "does at least one exist" only needs each chat's newest message, a one-row query. Read tracking is new to the data model — `riders/{uid}/chatReads/{chatId}` holds a `lastReadAt` timestamp, written by `ChatViewModel` on every snapshot its messages listener receives (covers "just opened it" and "stayed open while new ones arrived" with the one write, no separate mark-as-read action to remember). `firestore.rules` gained a nested `match /chatReads/{chatId}` under `riders/{riderId}`, owner-only, no shape validation needed since it's pure personal bookkeeping with no bearing on anyone else's data. `UnreadActivityViewModel` (shared at the `OffCampusNavHost` level, same pattern as the existing shared `FriendsViewModel`) watches the rider's own `friendIds` and every lobby their uid appears in `memberIds` for (the creator is always added to their own lobby's `memberIds` on posting, so one array-contains query covers "created" and "joined" both), and keeps one `ChatWatcher` per relevant chat — each just the newest-message timestamp and the rider's own read marker — added and torn down live as the relevant set changes (a friend removed, a lobby left never leaves a stale listener running). Verified for real on a physical phone, not the emulator: seeded genuine unread messages into a friend chat and a lobby chat via the Admin SDK, confirmed both the lobby's own card dot and the combined Friends-tab dot lit correctly, opened each chat in turn and confirmed each one's dot cleared individually while the combined alert correctly stayed lit until every source was read.

  **A real bug surfaced during that phone test, not caused by this fix but exposed by it**: switching from one signed-in account to another *without restarting the app* (sign out, then sign back in as someone else, all within the same still-running process) leaves several per-user ViewModels — `UnreadActivityViewModel` among them, but also the pre-existing `FriendsViewModel`, `ProfileViewModel`, and others that follow the same shape — still watching the *previous* account's data. Every one of these reads `Firebase.auth.currentUser?.uid` exactly once, inside `init {}`, when `viewModel()` first creates the instance for that Activity's lifetime; since `OffCampusNavHost`'s shared ViewModels are scoped to the Activity (which never gets destroyed by a sign-out alone, only by the process dying), a second account signing in on the same running instance never gets a fresh ViewModel — it just inherits whatever uid the first one captured. A real user hitting this in practice should be rare, since most Android builds (this project already documents OnePlus/OxygenOS's aggressive one) kill backgrounded apps often enough that a fresh process is the common case — but it's a genuine gap worth fixing properly (each affected ViewModel re-deriving its uid on every `FirebaseAuth` state change instead of once at construction) rather than working around by, say, force-killing the app between test accounts. Flagged here rather than silently worked around, since it was a broader architectural question — which ViewModels need this, and how — than "add an alert dot" was scoped to answer; fixed separately as Fix 13.

- **Fix 13 — Switching accounts without restarting the app no longer shows stale data** (fixes the bug Fix 12 found but didn't fix: `FriendsViewModel`, `PaymentNotificationViewModel`, `UnreadActivityViewModel`, `ProfileViewModel`, and the friend-graph half of `LobbyBrowseViewModel` all used to read `Firebase.auth.currentUser?.uid` exactly once inside their own `init {}`, open Firestore listeners for that one uid, and never look again — fine for the ordinary case where a ViewModel is created after sign-in and torn down at sign-out, but the first four are shared at the `OffCampusNavHost` level and live for the whole Activity's lifetime, so signing out and back in as someone else on the same still-running app left them holding the *previous* account's listeners and data). Deliberately left out: the screen-scoped ViewModels that take a navigation argument (`LobbyDetailViewModel`, `ChatViewModel`, `PostFareViewModel`, `PaymentSplitViewModel`, `RateRiderViewModel`, `ReportViewModel`, `TripHistoryViewModel`, `PostTripViewModel`) — these are tied to a specific lobby/chat/split id, get a fresh instance whenever their target changes, and sign-out's `popUpTo(0)` clears the whole back stack anyway, so they don't carry the same risk this fix is for. Verified for real, not just compiled: created a second throwaway test account, signed into it on the phone, confirmed the Friends tab correctly showed zero friends, then — **without force-stopping or restarting the app** — signed out and into the existing `testrider7` account, and confirmed both the Friends tab and the Profile tab updated immediately to `testrider7`'s own real data (a friend named "Aditi Rao", not the second account's empty list or any earlier session's leftovers). - **Fix 14 — Cold start with a persisted session flashed the sign-in form for a couple of seconds first** (bug report: opening the app while already signed in briefly showed the login screen before landing on Lobbies by itself). Root cause traced to a side effect of Fix 4: `AuthViewModel._uiState`'s starting value had been changed from a synchronous `auth.currentUser?.let { SignedIn(it.uid) } ?: SignedOut` guess to a plain `SignedOut` default, specifically to stop a magic-link user with no Rider document yet from ever being blindly treated as fully signed in. That fixed the magic-link race correctly, but it meant `AuthUiState.SignedOut` was now doing two different jobs at once — "definitely signed out" *and* "don't know yet" — and `OffCampusNavHost` always treated `SignedOut` as "show the sign-in form," so *every* cold start with a persisted session spent however long `resolveSignedInState()`'s Firestore read actually takes (a real network round trip, not instant) sitting on the sign-in screen before the answer came back and it jumped to Lobbies. Fixed by giving "don't know yet" its own state, `AuthUiState.Loading`, and making it the real starting value instead of `SignedOut`: `OffCampusNavHost`'s `LaunchedEffect` does nothing while in `Loading` (stays on AUTH's first frame, same as before), and `AuthScreen` renders a bare `CircularProgressIndicator` instead of the actual sign-in form for that state — so there's nothing for a returning rider to see flash before Lobbies opens. A genuinely signed-out rider is unaffected and still sees the form appear near-instantly, since that path (`addAuthStateListener` firing with `user == null`) was never the slow one — it needs no Firestore read at all. One knock-on fix `resolveSignedInState()` needed: its Firestore-error fallback used to just return whatever `_uiState.value` already was, which was safe when the only options were `SignedOut`/an already-resolved state, but would now strand a rider on the spinner forever if the *very first* resolution attempt hit a network error while still `Loading` — that one case now falls back to `SignedOut` (the same behavior this whole code path had before `Loading` existed), while a later resolution failing after a real state was already set still leaves that state untouched, exactly as before. Verified on a real cold start (force-stop, not just backgrounding) against an already-signed-in test account: lands on Lobbies with no visible sign-in screen at any point.

  **A second, subtler flash of the same kind survived Fix 14 and was only caught on screen recording**: even with `Loading` in place, a screen-recorded cold start still showed the real sign-in form — briefly, opaque, with the bottom nav bar already switched to Lobbies/Friends/Profile behind it — right at the moment `uiState` resolved from `Loading` to `SignedIn`. Root cause: `AuthScreen`'s own `if (uiState is AuthUiState.Loading) { ...spinner...; return }` only special-cased `Loading`; its `when` block below only special-cased `NeedsProfile`, so `SignedIn` fell through to the same `else -> PasswordStep(...)` branch as a genuinely signed-out user. `OffCampusNavHost`'s `LaunchedEffect(authState)` is what actually navigates away from AUTH once it sees `SignedIn`, but that's a separate effect that runs on a *later* recomposition, not synchronously with the state change — and Compose Navigation keeps the outgoing screen's composable alive and still recomposing (with `uiState` already `SignedIn`) for its own exit transition. `AuthScreen` had no way to tell "about to navigate away" apart from "show the form," so for that window it rendered the real form with real, empty fields — confirmed via `adb shell screenrecord` and reading the frames back frame-by-frame, since it happens well under a second and doesn't show up in `uiautomator dump` snapshots taken a beat too late. Fixed by folding `SignedIn` into the same early-return as `Loading` — both now render just the spinner, since neither is a state `AuthScreen` should ever be drawing its own content for. Verified the same way: screen-recorded several more cold starts and read every frame back — the exact frame that used to show the opaque sign-in form (bottom bar already on Lobbies, content area still resolving) now shows the spinner, with a clean fade straight into the Lobbies list right after.

- **Fix 16 — Uber-style place suggestions for the Gate and Destination fields** (feature request: typing part of a place name should show live suggestions to pick from, like Uber's pickup/drop-off fields, instead of typing the whole name exactly by hand). Google Places Autocomplete was the obvious first choice — it's literally what Uber uses, and Android even ships an `Autocomplete.IntentBuilder` that draws the whole picker UI for you — but that Intent is only a UI convenience over the same Places API, which still needs a billing-enabled Google Cloud project even to stay inside its free monthly credit, the same wall this project already hit and ruled out for Cloud Functions and Storage. Built instead on **Photon** (`photon.komoot.io`), a free public geocoder built on OpenStreetMap data — no API key, no billing, at the cost of being a shared best-effort community server rather than a paid SLA, and of OSM's data being volunteer-mapped (a small or brand-new local landmark might genuinely not be there yet, where Google's commercial data usually would be). New `PlaceSearchService.search(query)` (`data/PlaceSearchService.kt`) hits Photon's REST API with `lat`/`lon` bias parameters set to NMIMS's own campus coordinates — Photon treats this as a ranking hint, not a hard filter, so a search for a genuinely distant destination still returns real results, just not artificially boosted. New reusable `LocationAutocompleteField` composable (`ui/lobby/LocationAutocompleteField.kt`) wraps a plain `OutlinedTextField` in a `Box` with a manually-shown `DropdownMenu` underneath — deliberately not Material3's `ExposedDropdownMenuBox`, which is built for a fixed set of choices tied to focus/click state, not a suggestion list that changes on every keystroke. `PostTripViewModel` runs the same 300ms-debounced-search pattern `FriendsViewModel` already uses for friend search, one `Job` per field so gate and destination search independently; tapping a suggestion fills the field and stores its coordinates, typing further after that clears them back to `null` so a half-edited field can't silently keep posting a stale suggestion's location. `Lobby` gained optional `gateLat`/`gateLng`/`destinationLat`/`destinationLng` — `null` whenever the rider never picked a suggestion (the field still works as plain free text exactly like before, Photon just not knowing a place is never a hard failure), populated for free whenever they did, specifically so a later proximity/area-based feature (matching lobbies by "near me," not just exact text — a real, larger ask that came up in the same conversation) has real coordinates to work with instead of needing its own separate geocoding pass. Deliberately scoped to Gate and Destination only, per the request — Checkpoint and the Lobbies-screen "Search destination" filter are untouched.

  **A real, reproducible bug surfaced during testing, not in the UI code but in the network call itself**: the very first request to Photon after the app started often timed out (`SocketTimeoutException`) at the original 5-second timeout, even though the same query succeeded instantly from a plain `curl` and `ping` to Photon's host resolved in ~135ms — subsequent requests to the same host succeeded quickly and reliably. Read as a cold-connection cost (first-ever TLS handshake to a fresh host) landing right at the edge of an unnecessarily tight timeout for what's explicitly a free, best-effort public server — raised to 8 seconds connect/read, which is still well inside "the rider is still typing/reading, not stuck" and matches the tradeoff already documented for relying on Photon at all. Verified for real on the emulator, not just compiled: typed "Cooper Hospital" (the actual hospital by NMIMS's campus) into the Gate field and got it back as the top suggestion with its real Gulmohar Road, Vile Parle West address as the subtitle, alongside Photon's real nearby OSM entries for the same place; tapping it filled the field and closed the dropdown. Typing "Andheri" into Destination likewise returned real, live suggestions and selected cleanly. Posted the trip and read the document straight back with the Admin SDK to confirm `gateLat`/`gateLng`/`destinationLat`/`destinationLng` actually reached Firestore as real numbers, not just that the form looked right on screen. Confirmed the graceful-degradation path matters in practice, not just in theory: Photon's public instance is genuinely not 100%-reliable moment to moment, so the field's core promise — it's always still a normal text field underneath, a rider can just keep typing and post the trip either way — is doing real work, not just a defensive nicety.

- **Fix 17 — Polish pass on Fix 16's place suggestions: on-brand dropdown, a loading indicator, and a shorter timeout that still actually works** (three follow-up requests against Fix 16's first cut: the dropdown looked like a generic stock Material3 menu instead of part of this app, the field gave no feedback while a search was in flight, and 8 seconds felt too long to wait). The dropdown in `LocationAutocompleteField.kt` now uses `MaterialTheme.shapes.medium` (the ticket-stub shape every other card in the app uses), the theme's own surface color and `outline` border, and violet (`colorScheme.primary`) pin icons instead of Material3's default gray — the same `DropdownMenu` composable, just given the four style parameters (`shape`, `containerColor`, `border`, plus a matching icon tint) instead of accepting its defaults. `PostTripViewModel` gained `gateSearching`/`destinationSearching` flags, set `true` only once the 300ms debounce has elapsed and a request is actually sent (not while still debouncing each keystroke, which would flicker) and `false` once results land; the field renders a small `CircularProgressIndicator` as its trailing icon while that flag is set, so a real search in flight now looks different from a dead field.

  The timeout question took real measurement, not a guess, to answer honestly. Direct trials, four fresh queries each, no cherry-picking: **2 seconds failed 4/4**, **3 seconds failed 3/4** — both would have made the feature *usually* show nothing, not just show it a little slower, since Photon's real response time on a fresh connection routinely lands past both of those. That pointed at the actual bottleneck: the cold DNS+TLS handshake cost of the *first* request to a fresh host, not Photon's own lookup — so `PlaceSearchService.warmUp()` was added, a throwaway connection fired from `PostTripViewModel.init {}` the instant the post-trip screen opens, well before the rider reaches Gate or Destination. It exists purely to pay that handshake cost in the background while the rider is still on Checkpoint, so the pooled connection is already open by the time a real search needs it; best-effort only, wrapped in its own `try/catch` that swallows any failure, since a slow or failed warm-up should never block or change the outcome of the real search that follows it. With `warmUp()` in place, **4 seconds went 4/4** across the same four real queries (Cooper Hospital, Andheri, Koramangala, Juhu) — the shortest value that held up repeatedly, landed on by measuring, not by picking a rounder-looking number. The honest caveat, stated plainly rather than glossed over: this result assumes a couple of seconds naturally pass while filling in Checkpoint before the rider reaches Gate — if someone jumped straight to Gate within a second of opening the screen, the warm-up wouldn't have finished yet and the field would behave closer to a cold 4-second attempt, which the earlier 3-second trials suggest is still meaningfully less reliable than this measured-good case.

- **Fix 18 — Lobby search matches by area, not just exact text** (feature request: typing "Laxmi Industrial Estate" into the Lobbies screen's search bar should also surface a lobby headed to "Andheri West" or "Infinity Mall," since those are close enough that a rider living near one destination could reasonably join a lobby headed to the other and split the fare — not just lobbies whose destination text happens to contain the exact words typed). This is the feature Fix 16's `gateLat`/`gateLng`/`destinationLat`/`destinationLng` fields were deliberately added in advance for — building it now needed no new geocoding infrastructure, only a distance check on data that already exists. `LobbyBrowseViewModel.onDestinationQueryChange` now geocodes the typed text itself, the same 300ms-debounced `PlaceSearchService.search()` call Post Trip's Gate/Destination fields already use, taking the top result as "the place the rider means" (there's no dropdown to pick from on this field, unlike Post Trip — a search bar that pre-filters a list works differently from a field that becomes the posted data, so automatically taking the best match is the right tradeoff here, not a shortcut). - **Fix 20 — Lobby list scroll jank, measured rather than guessed at** (bug report: the Lobbies list doesn't scroll smoothly). Rather than change code on a hunch, this used `adb shell dumpsys gfxinfo <pkg> reset` before and after a scripted 4-swipe scroll sequence to get real janky-frame percentages and frame-time percentiles, seeding 30 throwaway lobbies first (via the Admin SDK, deleted again afterward) since the default handful of seeded lobbies wasn't enough to actually scroll. First finding, and an important one to name honestly: a cold-app first measurement looked dramatic (`animateContentSize()` on the `LazyColumn` seemed to roughly double jank versus removing it), but that dropped away almost entirely once both versions were measured *after* a few throwaway warm-up scrolls each — JIT compilation and GPU shader/shim warm-up on a fresh process dominate the first several seconds of any measurement on this emulator, badly enough to make an unfair single before/after comparison actively misleading. With that warm-up controlled for, `animateContentSize()` on the container showed no clear, repeatable effect either way — it was still removed (unusual to put on a scrolling container, and shape/position changes here don't need an animated resize), but documented as a code-quality cleanup, not a proven perf fix, since the measurements don't actually support that claim.

  The second hypothesis *did* hold up under the same fair, warmed-up comparison: each lobby card was wrapped in a per-item `AnimatedVisibility` (the Phase 0 brief's fade+scale-in for lobbies entering the filtered set) whose `remember { MutableTransitionState(false) }` started fresh, and therefore replayed its enter animation, every single time `LazyColumn` recomposed that item after recycling it back into view during a scroll — not just the one time a lobby is genuinely new. Measured with the animation removed entirely: steady-state jank dropped from ~5–10% (original code, warmed up) to ~3.5–5.4%, with the 90th-percentile frame time tightening from the high-20s/low-30s ms down to high-teens/low-20s ms — a real, repeatable difference, not noise. Deleting the animation outright would have broken the Phase 0 design brief's own requirement, though, so the actual fix keeps it but only for genuinely new lobbies: `LobbyBrowseScreen` now tracks which lobby ids have already played their entrance in a `mutableStateMapOf` scoped to the whole screen's lifetime (not reset by scroll, unlike each item's own `remember`), and an id already in that map starts its `MutableTransitionState` at `true` — already visible, no animation — while a genuinely new id still gets the full false→true fade+scale exactly as before. Measured this corrected version against the same warmed-up protocol: steady-state jank landed at ~3.5–4.5%, matching the animation-removed variant, confirming the fix isolates the actual cost (repeated animation replay) without touching the cases the design brief cares about.

- **Fix 21 — Gate/Destination suggestion dropdown was covering nearly the whole screen** (bug report on a real phone, with a screenshot: Fix 17's on-brand restyle of `LocationAutocompleteField`'s dropdown still looked plain next to Uber's own pickup/drop-off suggestion list, and — the more concrete problem — a common short query like "Andheri" returns enough OSM results that the unbounded `DropdownMenu` stretched from just under the field almost down to the keyboard, hiding the rest of the form entirely). Two separate changes: the `DropdownMenu` itself now gets `modifier = Modifier.heightIn(max = 260.dp)` (about 3.5 rows), so a long result list scrolls inside that fixed height instead of pushing the popup's own height out to cover the screen — `DropdownMenu`'s internal `Column` already scrolls, it just had nothing capping how tall it could grow first. Row content was also redone to read closer to Uber's own suggestion rows: the place name is now `FontWeight.SemiBold` instead of regular weight, the address subtitle is clamped to `maxLines = 1` (a long OSM address used to wrap to 2-3 lines per row, which was most of what made the list so tall), a thin `HorizontalDivider` (`outline` at 40% alpha) separates each row instead of relying on padding alone to tell rows apart, and each row's `contentPadding` was tightened from `DropdownMenuItem`'s roomy Material3 default to `16.dp` horizontal / `4.dp` vertical, closer to a real address-picker's row density. Verified on a real phone, not the emulator: typed "Andheri" into the Gate field (the exact query from the bug report) and confirmed the dropdown now stops at a fixed height with the rest of the form visible underneath, and that tapping a suggestion still fills the field and dismisses the dropdown correctly — the underlying suggestion logic from Fix 16/17 wasn't touched, this was purely how the list renders.

## Working method — phased, not linear
Work through phases in order (0 Design Brief → 1 Setup/Data Model → 2 Auth/Profile → 3 Lobby System → 4 Friends → 5 Chat → 6 Ride Booking Deep Links → 7 Payment Splitting → 8 Reporting → 9 Security Rules/Cloud Functions → 10 Aesthetic Polish → 11 Full Regression). After each phase: summarize what was built, run its checklist explicitly (pass/fail per item, not just "done"), fix failures and re-run the *whole* checklist (a fix can break something that previously passed), then wait for the user's go-ahead before starting the next phase. If something is ambiguous (design choice, data-model tradeoff), stop and ask rather than deciding silently.

## Firestore data model
- `riders` — name, avatar, rating, friends array
- `lobbies` — checkpoint, gate, destination, time, rideType, maxSize, members array, status, createdBy
- `friendRequests` — status: pending/accepted
- `chats` — lobby chats + persistent friend-to-friend chats, subcollection of messages (senderId, text, timestamp)
- `paymentSplits` — keyed by lobbyId: totalFare, paidBy, participants array (owedAmount, senderAck, receiverAck, settledStatus)
- `reports` — reportedBy, reportedUser, lobbyId, amount, reason, timestamp, status

## Rules
- Keep code readable and commented — the user needs to explain every part of it in a viva, so comment for a learner, not just non-obvious WHY.
- Prioritize a working, polished app over an ambitious broken one — if a phase is at risk, say which feature to trim rather than shipping something half-working.
- Explain real architectural tradeoffs (e.g. an awkward Firestore query pattern for the two-way ack model) instead of silently picking a workaround.
- Out of scope for this project (final report should list explicitly): real payments, live GPS, driver KYC, real ride-hailing API booking.
