# OffCampus

Last-mile ride-share Android app for college students: form travel "lobbies" heading the same way from a station/gate at a similar time, coordinate in-app chat, book the actual ride via Uber/Ola/Rapido deep links, split the fare with a two-way payment acknowledgement.

## Tech stack
- Kotlin, Jetpack Compose (Material 3) — no XML layouts
- Firebase: Authentication (college email), Firestore, Cloud Functions (matching/notification/acknowledgement logic)
- MVVM: ViewModel + StateFlow feeding Composables, no business logic inside Composables
- No payment gateway, no live GPS, no in-house driver network — ride booking hands off to Uber/Ola/Rapido via deep links

## Design system (Phase 0 — approved design brief lives at the artifact link in conversation history)
Concept: "streetlight & meter" — the actual moment of waiting at a gate at dusk for a shared auto. Quiet neutral surfaces; amber/violet/green/coral used only for actions and status, not decoration. Cards clip one corner like a ticket stub (`RoundedCornerShape(16,16,16,3)`); buttons stay full pill.

**Color roles (light / dark):**
- Background: `#F7F5FB` / `#171226`
- Surface: `#FFFFFF` / `#201A35`
- Primary (violet): `#6753E8` / `#9384FF`
- Action (amber): `#E8940E` / `#F5A524`
- Success/settled (green): `#1E9463` / `#3FCB90`
- Alert/owed (coral): `#D8492F` / `#FF7A5C`

**Typography:**
- Display/headlines: Bricolage Grotesque (bold, personality — app name, empty states, headers)
- Body/UI: Manrope (lists, chat, buttons)
- Numerals (fares, timestamps, seat counts): JetBrains Mono, tabular

**Spacing:** 4dp base grid — 4/8/12/16/24/32/48/64.

**Motion:** spring-based (damping ~0.8, ~200-300ms). Lobby list uses `AnimatedVisibility` (fade+scale) and `animateContentSize` for seat-count changes. Chat bubbles slide up 12dp + fade in. Payment ack crossfades chip color + morphs a checkmark on settle.

Once `Color.kt` / `Type.kt` / `Theme.kt` exist, every screen must use them — flag any screen that drifts during self-review.

Phase 9 (Security Rules / Cloud Functions): `firestore.rules` replaced the interim "any signed-in user can read/write anything" placeholder with real per-collection ownership rules — deployed to the live project and regression-tested against every write path in the app (join/leave/lock/complete a lobby, lobby and friend chat, friend-request accept, payment ack, filing a report). Two rules are deliberate, documented simplifications rather than oversights: `riders`' update rule carries a narrow carve-out letting one rider append themselves to *another* rider's `friendIds` (nothing else), because `FriendsViewModel.accept()` is still a two-client-write with no Cloud Function backing it; and `paymentSplits`' update rule only guarantees `totalFare`/`paidBy`/`participantIds` can't be tampered with, not that a participant can only flip their own ack flags (Firestore rules can't diff individual elements inside an array of maps) — that's still enforced by `PaymentSplitViewModel.acknowledge()`'s client-side transaction, same as before this phase. `ui/chat/ChatViewModel.kt`'s old `ensureParticipants()` (a client-writable mirror of chat membership, prone to a real race against the message listener) was removed in favor of the rules deriving membership straight from source data — a lobby chat's id against that lobby's own `memberIds`/`createdBy`, a friend chat's id split on `_` against the two uids it's made of. `functions/index.js` has Cloud Functions code (friend-accept as a proper one-sided admin write, real push notifications for a friend's new lobby and for money owed) written and documented for the report, but deliberately **not deployed** — that needs the Firebase project on a paid Blaze plan, a real billing decision left to whoever runs this project next; see that file's header comment for the exact deploy steps and the FCM-token gap that's still open even after deploying. Phase 10 (Aesthetic Polish): a full sweep against the Phase 0 design brief found colors, typography, and card shapes already compliant everywhere (`Color.kt`/`Type.kt`/`Theme.kt`/`Shape.kt` are the only source of those, no hardcoded hex or ad-hoc font sizes anywhere in `ui/`) — so this phase's actual work was the three specific motion specs the brief called out that hadn't been built yet: `LobbyBrowseScreen.kt`'s list now fades+scales each `LobbyCard` in/out (spring-based, matching the brief's damping/duration) as lobbies enter or leave the filtered set, and `LobbyCard.kt`'s seat dots animate their own fill color instead of snapping; `ChatScreen.kt`'s bubbles now slide up 12dp and fade in on first appearance (a `MutableTransitionState` flipped false→true right after composition, since a plain `visible = true` skips the enter transition when the bubble is already showing on its first frame — true every time, since each bubble is freshly composed when it's added to the list); and `PaymentSplitScreen.kt`'s "Settled" chip now scales+fades in a leading checkmark the moment a split settles, using the same false→true trick. ## Post-launch fixes
Bug fixes and small changes found after Phase 11 closed, not tied to any numbered phase.

- **Fix 1 — Auto capacity validation** (found during a post-completion test pass): `maxSize` was a flat 2-6 range regardless of ride type, so an Auto trip (a real auto-rickshaw seats 3 passengers, full stop) could be posted for a group of 4-6 — the default form state was even invalid out of the box (`maxSize = 4` paired with default `rideType = AUTO`). Fixed with `groupSizeOptions(rideType)` in `PostTripViewModel.kt` (Auto → 2..3, Cab → 2..6 unchanged), with the group-size selection auto-clamped down if it's out of range when switching to Auto. The same cap is now enforced in `firestore.rules`'s `lobbies` create rule too (deployed live), so a raw API call bypassing the app can't do it either. The two pre-existing seeded Auto lobbies that already violated this were patched in both `seed/seed.js` and the live Firestore data.

- **Fix 2 — Rider ratings** (feature gap: `ratingAverage`/`ratingCount` existed on `Rider` and rendered on `ProfileScreen.kt` since Phase 1, but nothing ever wrote to them — every rider showed "No ratings yet" forever). Added a new top-level `ratings` collection (`data/model/Rating.kt`: `lobbyId`, `raterUserId`, `ratedUserId`, `stars`, `timestamp`), doc id deterministically `{lobbyId}_{raterUserId}_{ratedUserId}` so rating the same person twice for the same trip corrects the existing document instead of double-counting. A "Rate" text action sits next to "Report" on every non-self participant row in `PaymentSplitScreen.kt` (plus a "Rate" link next to "Paid by ..." for participants rating the payer), opening `ui/rating/RateRiderScreen.kt` + `RateRiderViewModel.kt` — a 5-star picker matching the "★"/"☆" glyphs `ProfileScreen.kt` already used to display ratings read-only. `RateRiderViewModel.submit()` runs one Firestore transaction that reads any prior rating from this rater for this trip, reads the rated rider's current rollup, and writes both the rating doc and the adjusted `ratingAverage`/`ratingCount` atomically — same transaction-first pattern as `PaymentSplitViewModel.acknowledge()`. `firestore.rules` gained a third narrow `riders` update carve-out (`isRatingUpdate`) alongside the friendIds one from Phase 9, with the same honest limit: the rule can confirm the *result* lands in a plausible range (count holds steady or grows by exactly one, average stays in [0, 5]), not that the arithmetic that produced it was honest — a real fix needs a Cloud Function to own the computation, same conclusion as the payment-ack case. Scope choice: rating only covers payer↔participant pairs (mirroring where Report already lives), not participant-to-participant when neither is the payer — the payment split screen has no UI slot for that today. One real bug found and fixed during testing: the `ratings` read rule originally dereferenced `resource.data` unconditionally, which denies outright when the document doesn't exist yet — and `RateRiderViewModel.submit()`'s transaction always reads that exact doc first (to check for a prior rating) before it necessarily exists, so every first-ever rating failed with `PERMISSION_DENIED` until the rule was changed to allow reading a not-yet-existing document.

- **Fix 3 — Passwordless college-email sign-in** (feature request: sign in with just a college email, no password, the way Google apps let you "continue" without retyping a password). Went with Firebase Auth's **email link** ("magic link") method rather than Google Sign-In, since Google Sign-In only proves anything if the college's student email is actually Google-Workspace-backed, which isn't something this project can verify — email link works with any real inbox. The harder part wasn't Firebase Auth itself, it was getting the link to open *this app* instead of a browser: **Firebase Dynamic Links — the service that used to make an email-link URL smart enough to hand off to a mobile app — shut down in 2025**, so that hand-off now has to be built by hand with real Android **App Links**. `public/index.html` + `public/.well-known/assetlinks.json` are deployed to Firebase Hosting (`offcampus-5f370.web.app`), `assetlinks.json` declares the app's signing certificate so Android will trust the association, and `AndroidManifest.xml`'s `MainActivity` gained a second, `autoVerify="true"` intent-filter for that host plus `launchMode="singleTop"` so a link tapped while the app is already open re-delivers through `onNewIntent` instead of spawning a second instance. `AuthViewModel.sendMagicLink()` calls `sendSignInLinkToEmail` with an `ActionCodeSettings.url` pointing at that hosted page, and stashes the email in `SharedPreferences` (`PREF_PENDING_EMAIL`) — Firebase's own completion call needs the email back, and the link itself doesn't carry it. `MainActivity` forwards whatever URI launched or re-launched it to `AuthViewModel.handleEmailLinkIntent()`, which no-ops unless `auth.isSignInWithEmailLink()` recognizes it. One real gap the password flow never had: a magic link creates the Firebase Auth user immediately on tap, with no separate step that ever asked for a name — so `AuthUiState` gained a `NeedsProfile` case, and `AuthScreen` shows a one-time "what's your name?" step (`completeProfile()`) before treating a fresh magic-link signup as fully signed in; a returning user with an existing Rider doc skips straight through. Two deliberate limitations, both flagged in-code: completing the link only works on the same device/app install that requested it (the pending email lives in that install's own SharedPreferences, not synced anywhere); and `assetlinks.json` currently only lists this machine's **debug** keystore's SHA-256 fingerprint — a release build's own signing certificate has to be added as a second entry in that file before a signed release APK's links would verify. Verified end-to-end against the live Firebase project (not just compiled): enabled the Email Link provider on the project (it ships disabled), generated real sign-in links via the Admin SDK for a throwaway test account, and drove the whole chain on the emulator — send → tap → sign-in → name step → Rider doc created → avatar picker — confirming both server-side (a real Firebase Auth user and Firestore Rider doc were created) and on-screen. One `adb`-only gotcha surfaced along the way: `adb shell` re-parses `&` through the device's own shell, silently truncating a URL's query string unless each `&` is escaped — worth knowing if this flow ever needs re-testing by hand from a shell; it isn't a bug in the app.

A **real bug** did surface, though, the first time this was tested against an actual inbox rather than a throwaway Admin-SDK link: tapping a genuine email link dropped the account straight into the Lobbies screen with **no Rider document ever created** — skipping the name step entirely. Root cause: `AuthViewModel`'s `addAuthStateListener` (there since Phase 2, to restore a persisted session on cold start) fires the instant Firebase's SDK completes `signInWithEmailLink`, same as any other auth-state change — and it unconditionally set `AuthUiState.SignedIn`, with no notion that a magic-link user might not have a Rider document yet. That write raced the deliberate Rider-doc check already sitting at the end of `handleEmailLinkIntent`, and the listener's blind write was winning. Fixed by giving both paths one shared `resolveSignedInState(uid, email)` — it's the only place that decides `SignedIn` vs `NeedsProfile` now, so the two can race all they want and still land on the same correct answer. On a Firestore read failure it deliberately leaves `uiState` untouched rather than guessing `NeedsProfile` for an already-registered user — `completeProfile()` does a full document `set()`, so guessing wrong there would have overwritten a real user's avatar/ratings/friends with fresh defaults.

- **Fix 7 — `assetlinks.json` had the wrong signing fingerprint** (found installing the app on a real phone via USB for the first time, not the dev machine's emulator). App Links verification kept failing silently — `assetlinks.json` listed the SHA-256 of a debug keystore generated once by hand at `~/.android/debug.keystore` while chasing an unrelated JDK issue, but `./gradlew signingReport` showed Gradle's *actual* debug build was signed with a completely different keystore living at `D:\Android\.android\debug.keystore` — two debug keystores existed on the same machine, and the one the file vouched for was never the one signing real builds. Fixed by publishing the real fingerprint from `signingReport` and deleting the unused hand-made keystore so it can't cause the same confusion again. Worth remembering for anyone re-running this project fresh: **always confirm the fingerprint with `signingReport` right before touching `assetlinks.json`**, don't assume any single `debug.keystore` path is the one in play — Android Studio, a plain `gradlew` invocation, and a manually created keystore can all disagree about which file that is.

## Working method — phased, not linear
Work through phases in order (0 Design Brief → 1 Setup/Data Model → 2 Auth/Profile → 3 Lobby System → 4 Friends → 5 Chat → 6 Ride Booking Deep Links → 7 Payment Splitting → 8 Reporting → 9 Security Rules/Cloud Functions → 10 Aesthetic Polish → 11 Full Regression). After each phase: summarize what was built, run its checklist explicitly (pass/fail per item, not just "done"), fix failures and re-run the *whole* checklist (a fix can break something that previously passed), then wait for the user's go-ahead before starting the next phase. If something is ambiguous (design choice, data-model tradeoff), stop and ask rather than deciding silently.

## Firestore data model
- `riders` — name, avatar, rating, friends array
- `lobbies` — checkpoint, gate, destination, time, rideType, maxSize, members array, status, createdBy
- `friendRequests` — status: pending/accepted
- `chats` — lobby chats + persistent friend-to-friend chats, subcollection of messages (senderId, text, timestamp)
- `paymentSplits` — keyed by lobbyId: totalFare, paidBy, participants array (owedAmount, senderAck, receiverAck, settledStatus)
- `reports` — reportedBy, reportedUser, lobbyId, amount, reason, timestamp, status

## Rules
- Keep code readable and commented — the user needs to explain every part of it in a viva, so comment for a learner, not just non-obvious WHY.
- Prioritize a working, polished app over an ambitious broken one — if a phase is at risk, say which feature to trim rather than shipping something half-working.
- Explain real architectural tradeoffs (e.g. an awkward Firestore query pattern for the two-way ack model) instead of silently picking a workaround.
- Out of scope for this project (final report should list explicitly): real payments, live GPS, driver KYC, real ride-hailing API booking.
